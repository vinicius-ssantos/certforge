| `iv286-arraylist-vs-linkedlist-access-pattern` | B | Oracle Java SE 21 `ArrayList` API explicitly documents constant-time indexed `get`; `LinkedList` and `List` API document sequential access, so repeated index lookup is less efficient. The alternatives wrongly treat resizing as dominant, deny ArrayList append, or conflate shared interface with shared complexity. |
| `iv288-self-invocation-bypasses-transactional-proxy` | B | Spring Framework **Understanding AOP Proxies** explicitly documents self-invocation via `this` bypasses proxy advice. Alternatives incorrectly assume automatic interception, startup validation, or implicit weaving. |
| `iv288-profile-specific-bean-missing-from-active-profile` | B | Official Spring Boot **Profiles**: when no explicit active profile exists, the fallback profile is `default`, **not** `prod`. `@Profile("prod")` therefore keeps the sole FileStorage bean unregistered and mandatory injection unsatisfied. The three wrong options invent implicit `prod` activation, wildcard profile activation, or automatic registration of **this** prod-scoped bean. Codex P2 found that the earlier D rationale falsely limited default-fallback registration to `@Profile("default")`: unprofiled beans and matching negated expressions such as `@Profile("!prod")` can register. The corrected D explanation is supported by Spring Framework 6.2 `@Profile` Javadoc. |
| `iv288-component-scan-bean-not-found` | B | Spring Framework `@ComponentScan` Javadoc and Spring Boot **Structuring Your Code** explicitly make default scan recursive under the main application class package. `com.example.billing` is a sibling, not a child of `com.example.orders`; `@Service` alone doesn't bring it into that scan. The alternatives wrongly limit scanning to exactly one package, demand a `@Bean`, or claim that **only** packages configured through `spring.main.sources` are scanned. Codex P2 correctly noted that `spring.main.sources` **exists** and can add sources, including scanned packages, while `@SpringBootApplication` still triggers its own default scan. The corrected D explanation and new Spring Boot properties / `SpringApplication` Javadoc references capture this distinction. |
| `iv288-property-source-precedence-env-vs-yaml` | C | Official Spring Boot **Externalized Configuration** orders packaged application config below OS environment, and command-line `--server.port` above both in the default property-source precedence, yielding **7070** rather than 8080/9090. Conflicting declarations are resolved, not rejected. |
| `iv288-transactional-propagation-required-vs-requires-new` | B | Spring Framework **Transaction Propagation** documents that `REQUIRES_NEW` executes an independent physical transaction, so committed audit work survives an outer `REQUIRED` transaction's subsequent rollback. The distractors mistake it for `REQUIRED`, link it to exception catching, or confuse isolation with propagation. |
