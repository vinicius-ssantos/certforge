## Original publisher technical evidence

1. **Page count**: Spring Data's own PageableExecutionUtils explicitly documents that constructing a Page **omits a count query when the total is determined by the result size and Pageable**. The old question's correct option C incorrectly claimed at least two statements *on every call*. Corrected C expresses common separate COUNT and the skip optimization. Original source https://docs.spring.io/spring-data/commons/docs/current/api/org/springframework/data/support/PageableExecutionUtils.html and prior Spring Data JPA query methods reference.

2. **Pessimistic locking**: `LockModeType.PESSIMISTIC_WRITE` serializes competing updates or conflicting row-lock acquisitions. PostgreSQL's official row-locking docs distinguish ordinary unblocked SELECTs from conflicting row locks/UPDATEs under MVCC; old answer D and overall explanation incorrectly said *any other transaction reading* a row blocks. Corrected D scopes the guarantee to conflicting locking reads/writes and requires reading/rechecking seat state under the lock. Original source https://www.postgresql.org/docs/current/explicit-locking.html and Jakarta Persistence LockModeType reference.

3. **Native query mapping**: Original B incorrectly required an explicit @SqlResultSetMapping or DTO constructor mapping for any structured native result. Spring Data JPA supports interfaces, raw Object[]/tuple/map and explicit DTO mappings when suitable. The genuine trade-off is literal vendor SQL/dialect portability plus deliberate result shaping for a non-entity window query. Source https://docs.spring.io/spring-data/jpa/reference/jpa/query-methods.html.

4. **Template Method vs Strategy**: Independent Codex review of PR #520 found a false claim that composition cannot enforce an invariant pipeline. The corrected explanation makes clear Strategy can be combined with a central ReportJob.run() to enforce ordering, whereas option A as rewritten explicitly lacks that shared skeleton. Correct key remains C as a direct Template Method example. Original author-hosted source: https://refactoring.guru/design-patterns/template-method#relations. The PR #520 review is withdrawn for this question; independent V2 re-review occurs only after this source-only correction merges.

5. **Repository vs DAO correction**: A second independent Codex finding on PR #520 identified an unsupported categorical claim that a JpaRepository cannot be a real Repository merely because several callers perform additional duplicated filtering. The updated A and rationale explicitly recognize Spring Data's ability to implement the Repository pattern; the actual problem is uncentralized domain eligibility and pagination logic, which must be consolidated in one business-facing query/service. Original publisher sources: https://martinfowler.com/eaaCatalog/repository.html and https://docs.spring.io/spring-data/jpa/reference/repositories/core-concepts.html.
