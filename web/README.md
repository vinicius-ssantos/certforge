# CertForge web

Learner web app (React 19, TypeScript, Vite). See [ADR 0009](../docs/adr/0009-web-frontend-stack.md).

## Run

```sh
npm ci
npm run dev        # http://localhost:5173, proxies /api to the backend on :8080
```

Start the backend first (see the root README). The app is same-origin with the API, so no CORS setup or token handling is needed.

## Checks

```sh
npm run lint       # ESLint, including jsx-a11y
npm run typecheck
npm test           # Vitest, Testing Library, vitest-axe
npm run api:check  # generated types match openapi.json
npm run build
```

## End-to-end tests

**Warning:** The test suite writes and publishes fake questions and synthetic exam objectives. It must never run against the persistent learner installation at `:8081` or the clean review installation at `:8082`. Use `just e2e-release` (separate project, ports and volume; test frontend on `http://127.0.0.1:8083`). Local manual E2E runs require `CERTFORGE_E2E_DISPOSABLE=1` and `E2E_API_URL=http://127.0.0.1:8086` on the dedicated disposable Compose backend; the guard rejects all other API ports (including Vite dev proxy :5173) and unqualified runs. CI uses disposable services.

Playwright drives the real application (built web app, Spring Boot backend, PostgreSQL) on desktop and mobile viewports, and runs axe on every page it visits. CI does this in the `e2e` job.

For local runs use a **disposable and isolated** stack, never the app/database serving your own study history:

```sh
# from the repository root
just e2e       # alias for just e2e-release; dedicated web :8083, API :8086
```

If Playwright browsers are not yet installed, run `cd web && npx playwright install chromium` once. To drive the isolated Compose API manually, start the `certforge-e2e` stack and set `CERTFORGE_E2E_DISPOSABLE=1` and `E2E_API_URL=http://127.0.0.1:8086`, then run `npm run e2e` **without** `E2E_BASE_URL`. Playwright starts its own Vite preview on :4173 and explicitly proxies browser `/api` traffic to that same disposable `E2E_API_URL`. The preview never reuses an unknown listener on :4173. For an existing web stack, `E2E_BASE_URL` is allowed locally only for the repository's dedicated :8083 frontend paired with the :8086 backend (as in `just e2e-release`). The E2E safeguards use an allowlist for the sole local API port `:8086`, rejecting every other port, including frontend development proxies that redirect `/api` to a persistent database. This policy intentionally does not permit arbitrary custom local API ports. It validates the configured port, not the underlying process or database identity; always launch the dedicated `certforge-e2e` Compose project first. CI manages a separate ephemeral database.

The fixtures are test data. The Java SE 21 content pack awaits human review and is never published by automation.

## The API contract

`openapi.json` is generated by the backend, never edited by hand. After changing a controller or view:

```sh
./mvnw -Dtest=OpenApiContractIT -Dopenapi.update=true verify   # from the repo root
npm run api:generate                                        # from web/
```

Commit both files. CI fails when they are stale.

### Installation support link

Set `VITE_SUPPORT_URL` at frontend build time to an installation-owned `https://`
URL or `mailto:` address. The sign-in help exposes this public contact link; do
not put credentials or private tokens in it. Unsupported schemes are ignored.
When unset, help explicitly says that no support channel is configured and directs
visitors to reply to the invitation/message containing the installation address.
This setting does not add a password-reset service or disclose account details.
