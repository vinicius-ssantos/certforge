# Revisão de prontidão da v0.1.0

> Tradução de [`docs/release/v0.1.0-readiness.md`](../../docs/release/v0.1.0-readiness.md). O inglês é a fonte canônica.

Issue #15. Escrita em 2026-10-01 sobre a `main`; atualizada em 2026-10-02, quando a revisão do pacote de conteúdo foi feita e registrada.

## Veredito

**Não está pronta para receber a tag.** Toda barreira que um software consegue segurar passa no CI. O que resta precisa de uma pessoa e está listado em [Bloqueios](#bloqueios). Nenhuma tag `v0.1.0` nem release no GitHub foi criada, de propósito.

## O que a validação encontrou

Rodar as imagens reais atrás do proxy real achou problemas que os testes anteriores não podiam achar. Todos estão corrigidos e agora protegidos:

- Avisos críticos e altos no Tomcat e no Jackson, como gerenciados pelo Spring Boot 4.1.1, além de pacotes do sistema operacional desatualizados nas duas imagens.
- A Content Security Policy estrita teria bloqueado as fontes do app em produção, porque o build as embutia como URIs `data:`.
- Atrás de um proxy todos os usuários dividiriam um balde de limitação, e um proxy que acrescentasse ao `X-Forwarded-For` deixaria o cliente escolher o próprio endereço.
- Erros que o framework web levanta antes de um controller rodar (caminho desconhecido, método ou tipo de conteúdo errado) não tinham código estável nem id de requisição.
- O Flyway procurava a tabela de histórico no schema errado quando o usuário do banco se chama `certforge`, como na configuração documentada: a prontidão ficava `DOWN` e a próxima subida falhava. (Achado antes, no #13.)

## Linha de base de desempenho

Medida em 2026-10-01 com o `deploy/measure-baseline.mjs`: um aluno, requisições sequenciais pelo proxy nginx, 30 rodadas, backend e PostgreSQL no Docker Desktop em um notebook de desenvolvimento, Java 25. **É uma linha de base para notar regressões, não uma afirmação de capacidade.**

| Fluxo | p50 (ms) | p95 (ms) | Orçamento p95 (ms) |
|---|---:|---:|---:|
| entrar | 58 | 64 | 1500 |
| listar trilhas | 7 | 10 | 400 |
| iniciar sessão | 16 | 20 | 600 |
| ler sessão | 8 | 11 | 400 |
| enviar resposta | 11 | 16 | 600 |
| terminar sessão | 9 | 12 | 600 |
| ler histórico | 8 | 12 | 500 |
| ler progresso | 8 | 13 | 500 |

Inicialização do backend 6,6 s (orçamento 30 s). App web no primeiro carregamento: JavaScript 125 KB e CSS 4 KB, comprimidos com gzip (orçamentos 170 KB e 12 KB). Os orçamentos são várias vezes a linha de base para que um runner compartilhado lento não os viole e uma regressão real viole; o CI aplica todos.

## Barreiras que rodam a cada mudança

Backend: build, formatação, PMD, 150 testes de integração no PostgreSQL. Web: lint com regras de acessibilidade, checagem estrita de tipos, testes unitários, build de produção, orçamento de tamanho, `npm audit`. Ponta a ponta: a suíte do Playwright duas vezes, uma no servidor de desenvolvimento e outra nas imagens de release. Imagens de release: varredura de vulnerabilidades, checagens de proxy e cabeçalhos, ensaio de restauração, orçamentos de desempenho, inspeção de privacidade. Repositório: varredura de segredos de todo o histórico, CodeQL para Java e TypeScript, Dependabot.

## Bloqueios

Estes precisam de uma pessoa. Nenhum se fecha com mais automação.

1. **Conferir o texto dos objetivos do exame com a página da Oracle.** Os nomes de tópico e o texto dos objetivos semeados por `V4__seed_java_certification_catalog.sql` vêm em parte de resumos secundários, porque a página de exame da Oracle é renderizada por JavaScript e recusa clientes automatizados; três linhas em especial precisam de uma pessoa para comparar no navegador. A tela de catálogo lista esse texto para a versão de exame ativa, tópico a tópico, que é o lugar mais fácil para fazer isso. Isto é um portão para publicar na trilha, não para as questões em si.

   As questões foram revisadas: em 2026-10-02 o dono do projeto leu as vinte no [pacote de revisão de conteúdo](../../docs/release/content-review-packet.md) e não relatou nenhum erro técnico, registrado em [`content/java-se-21/review.json`](../../content/java-se-21/review.json). Esse registro guarda um digest de cada questão revisada, então editar uma depois faz com que ela volte a contar como não revisada, em vez de herdar o veredito. O que a revisão **não** estabelece está listado no pacote: o revisor é o dono do projeto, não um terceiro independente, e quatro questões não têm código executável, então nada mecânico as sustenta.
2. **Revisão manual de acessibilidade (#13, #14).** Seguindo o Roteiro C dos [roteiros de demonstração](demo-scripts.md). As verificações automáticas agora cobrem contraste nos dois esquemas de cor, refluxo até 320 pixels, todo controle alcançável pelo Tab com anel de foco visível, e a árvore de acessibilidade de onde um leitor de tela lê. O que sobra é o que uma máquina não julga: se a ordem de tabulação faz sentido, se as mensagens de status são de fato anunciadas e em ordem sensata, e se os layouts escuro e ampliado são confortáveis.
3. **Um primeiro passeio humano.** Alguém que não seja o autor segue os Roteiros A e B dos [roteiros de demonstração](demo-scripts.md) e diz se faz sentido.
4. **Decisões para a primeira implantação** (não são código): quem termina o TLS, com que frequência os backups rodam e onde ficam, e os objetivos de recuperação. A [ADR 0010](../adr/0010-first-deployment-posture.md) propõe uma resposta para cada uma, com o raciocínio, então agora é uma decisão a aceitar ou alterar, não uma página em branco.

## Para lançar quando os bloqueios estiverem fechados

1. Feche #13, #14 e #15, depois o épico #2 e o marco. (A #8 foi fechada em 2026-10-02 com a revisão registrada.)
2. Importe o pacote na instância que vai servi-lo (`just import-content`) e faça uma conta revisora aprovar e um administrador publicar as questões. A revisão registrada é o julgamento técnico; a mesa editorial é onde isso se torna uma revisão publicada, com procedência de autor e revisor. Até isso acontecer, uma instalação nova não tem questões.
3. Defina a versão: `0.1.0-SNAPSHOT` para `0.1.0` no `pom.xml` (o app web já é `0.1.0`) e `[Unreleased]` para `[0.1.0]` no changelog.
4. Transforme as [notas de release](v0.1.0-release-notes.md) de rascunho em texto final, com a data.
5. Crie a tag `v0.1.0` no commit cujo CI está verde e crie a release no GitHub a partir das notas.
