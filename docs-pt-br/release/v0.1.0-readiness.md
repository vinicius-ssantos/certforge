## O que a validação encontrou

Rodar as imagens reais atrás do proxy real achou problemas que os testes anteriores não podiam achar. Todos estão corrigidos e agora protegidos:

- Avisos críticos e altos no Tomcat e no Jackson, como gerenciados pelo Spring Boot 4.1.1, além de pacotes do sistema operacional desatualizados nas duas imagens.
- A Content Security Policy estrita teria bloqueado as fontes do app em produção, porque o build as embutia como URIs `data:`.
- Atrás de um proxy todos os usuários dividiriam um balde de limitação, e um proxy que acrescentasse ao `X-Forwarded-For` deixaria o cliente escolher o próprio endereço.
- Erros que o framework web levanta antes de um controller rodar (caminho desconhecido, método ou tipo de conteúdo errado) não tinham código estável nem id de requisição.
- O Flyway procurava a tabela de histórico no schema errado quando o usuário do banco se chama `certforge`, como na configuração documentada: a prontidão ficava `DOWN` e a próxima subida falhava. (Achado antes, no #13.)

## Linha de base de desempenho

Medida em 2026-10-01 com o `deploy/measure-baseline.mjs`: um aluno, requisições sequenciais pelo proxy nginx, 30 rodadas, backend e PostgreSQL no Docker Desktop em um notebook de desenvolvimento, Java 25. **É uma linha de base para notar regressões, não uma afirmação de capacidade.**

| Fluxo | p50 (ms) | p95 (ms) | Orçamento p95 (ms) |
|---|---:|---:|---:|
| entrar | 58 | 64 | 1500 |
| listar trilhas | 7 | 10 | 400 |
| iniciar sessão | 16 | 20 | 600 |
| ler sessão | 8 | 11 | 400 |
| enviar resposta | 11 | 16 | 600 |
| terminar sessão | 9 | 12 | 600 |
| ler histórico | 8 | 12 | 500 |
| ler progresso | 8 | 13 | 500 |

Inicialização do backend 6,6 s (orçamento 30 s). App web no primeiro carregamento: JavaScript 125 KB e CSS 4 KB, comprimidos com gzip (orçamentos 170 KB e 12 KB). Os orçamentos são várias vezes a linha de base para que um runner compartilhado lento não os viole e uma regressão real viole; o CI aplica todos.

## Barreiras que rodam a cada mudança

Backend: build, formatação, PMD, 150 testes de integração no PostgreSQL. Web: lint com regras de acessibilidade, checagem estrita de tipos, testes unitários, build de produção, orçamento de tamanho, `npm audit`. Ponta a ponta: a suíte do Playwright duas vezes, uma no servidor de desenvolvimento e outra nas imagens de release. Imagens de release: varredura de vulnerabilidades, checagens de proxy e cabeçalhos, ensaio de restauração, orçamentos de desempenho, inspeção de privacidade. Repositório: varredura de segredos de todo o histórico, CodeQL para Java e TypeScript, Dependabot.

## O que uma pessoa conferiu

Estes não podiam ser fechados com mais automação. Todos foram feitos em 2026-10-02 pelo dono do projeto.

1. **O pacote de conteúdo (#8).** As vinte questões lidas no [pacote de revisão de conteúdo](../../docs/release/content-review-packet.md), sem nenhum erro técnico relatado, registrado em [`content/java-se-21/review.json`](../../content/java-se-21/review.json). Esse registro guarda digests de cada questão revisada, então editar uma depois faz com que ela volte a contar como não revisada em vez de herdar o veredito, enquanto escrever um programa para uma que não tinha o mantém. O que a revisão **não** estabelece está listado no pacote: o revisor é o dono do projeto, não um terceiro independente, e três questões não têm código executável, então nada mecânico as sustenta.
2. **O texto dos objetivos do exame (#68).** Comparado com a [página da prova](https://education.oracle.com/java-se-21-developer-professional/pexam_1Z0-830) da Oracle em um navegador e relatado como coincidente, incluindo as três linhas sobre as quais os resumos secundários divergiam. Nenhuma migration foi necessária. A página recusa clientes automatizados, então nada reconfere isso: é uma coincidência em 2026-10-02, a ser comparada de novo quando a Oracle revisar o exame.
3. **Revisão manual de acessibilidade (#13, #14).** O Roteiro C dos [roteiros de demonstração](demo-scripts.md), cobrindo o que uma máquina não julga: se a ordem de tabulação faz sentido, se as mensagens de status são anunciadas e em ordem sensata, e se os layouts escuro e ampliado são confortáveis. Nada a corrigir foi relatado. As verificações automáticas continuam cobrindo contraste nos dois esquemas de cor, refluxo até 320 pixels, alcance por Tab com anel de foco visível e a árvore de acessibilidade.
4. **O primeiro passeio.** Os Roteiros A e B, contra uma instância com o pacote real publicado em vez de dados de demonstração, o que o `just publish-content` tornou possível. Nada a corrigir foi relatado.
5. **As decisões da primeira implantação.** A [ADR 0010](../adr/0010-first-deployment-posture.md) aceita como escrita, junto com a [ADR 0011](../adr/0011-grade-content-evidence.md) e a [ADR 0012](../adr/0012-interface-language.md).

### A que isso não equivale

- **Uma pessoa, que também é o autor.** O passeio foi escrito originalmente como "alguém que não seja o autor segue os Roteiros A e B", e essa forma mais forte não foi atendida: a mesma pessoa escreveu o projeto, revisou o conteúdo e fez o passeio. Um segundo par de olhos segue sendo a coisa mais valiosa que esta release não teve.
- **Aceitar a ADR 0010 não é implantar conforme ela.** Terminação de TLS, backups fora do host e os objetivos de recuperação estão decididos; uma implantação ainda precisa ser montada conforme, e o [guia de operações](../engineering/operations.md) diz como.
- **Nada é publicado até alguém publicar.** Uma instalação nova não tem questões; o `just reviewer` e o `just publish-content` levam o pacote revisado pelo fluxo editorial na instância que vai servi-lo.
