# Changelog

All notable changes to CertForge will be documented here.

The project follows Semantic Versioning. Changes land under `Unreleased` and move to a version when it is tagged.

## [Unreleased]

### Added

- Twenty-four more, taking the pack to **124 of 150** proved by the build, and with it every remaining question of topics 1 to 6. Among them: the `Integer` cache guaranteeing `==` only for -128 to 127, the enhanced-for variable being a copy the array never sees, `case null` matching a null selector where a pattern switch otherwise throws, `case null, default` being the one arm allowed to carry both, an enum constructor being implicitly private, a private interface method serving a default method without entering the implementing class's public API, `final`, `sealed` and `non-sealed` each satisfying a direct subclass of a sealed class, `AutoCloseable.close()` declaring `Exception` where `Closeable` narrows it to `IOException`, an override being free to drop or narrow a checked exception, `try (reader)` closing a resource the statement did not declare, `? extends Number` reading as `Number` while `? super Integer` accepts an `Integer` and reads as `Object`, defaults and statics and abstract redeclarations of `Object` methods all leaving an interface functional, `this` in a lambda being the enclosing instance where an anonymous class's is not, and `filter` processing nothing before a terminal operation while `sorted` consumes every input before emitting one. Six of the twenty-four are proved by **not** compiling — a non-exhaustive switch expression, two unrelated defaults without an override, two overloads clashing on the same erasure, a subclass catch placed after its superclass, an assignment to a multi-catch parameter, and `List<Integer>` assigned to `List<Number>` — each pinned to the diagnostic the compiler actually reports rather than to the absence of a class file (#84).
- Fourteen more, taking the pack to **100 of 150** proved by the build. `stripTrailingZeros` producing a negative scale, `withDayOfMonth(31)` on April throwing rather than clamping, a leap day plus a year landing on the 28th, the dangling else binding to the nearest unmatched `if`, a `do` body running with a condition that was false from the start, a superclass method winning over an interface default, a record's component being a private final field with a public accessor and no setter, `LinkedHashMap.firstEntry()` in encounter order, `String::length` fitting `ToIntFunction`, `join()` throwing unchecked where `get()` throws checked, `startVirtualThread` returning a started virtual thread, `Files.readString` defaulting to UTF-8 rather than the platform charset, and a bundle key resolving through its parent (#84).
- Seventeen more questions of the expansion carry a verification program, taking the pack from 69 to 86 of 150 proved by the build. Among them: `BigDecimal` division without a rounding mode throwing rather than guessing a precision, `Math.round(-1.5)` being -1 and not -2, `throw null` compiling and then throwing, precise rethrow letting a method declare the two exceptions its body can actually throw, `Arrays.asList` writing through to the array while refusing to grow, a `TreeSet` comparator deciding membership instead of equals, an unmodifiable view seeing changes to the list behind it, `toMap` refusing a duplicate key, `computeIfAbsent` recording nothing when the function returns null, and `Files.copy` refusing an existing target. Each program prints booleans and ASCII tokens only, so the expected output does not depend on the platform or the default locale (#84).

## [0.2.0] - 2026-10-03

Adaptive Review. See the [release notes](docs/release/v0.2.0-release-notes.md) for what it does and what it does not.

### Fixed

- The deploy scripts explain a failed administrator sign-in instead of printing a stack trace. The bootstrap administrator is created only when the database has none, so pointing BOOTSTRAP_ADMIN_EMAIL at a different address later does nothing at all, silently, and the 401 that follows looks like a wrong password. The scripts now say that and suggest the fix, and the release environment guide calls the trap out next to the sentence that hides it.
- Answering a question did not refresh the review queue, the misconception counts, progress or history, which are all derived from attempts. Queries stay fresh for 30 seconds, and practising one question takes less, so a learner who practised a queued question and went straight back to the queue was shown the state from before they answered. Found by the new end-to-end test of the loop, which is the only place the two halves meet.

### Added

- Mock-exam foundation for 1Z0-830: an explicit 50-question / 120-minute / 68% practice blueprint, a balanced planner that selects five published questions from each of the ten current top-level topics and shuffles the full run, plus the architecture contract that keeps answer material hidden until a future persisted mock closes (#97, ADR 0015).
- `GET /api/review/misconceptions` and a section on the progress screen showing where a learner has been wrong while saying they were confident, per topic. **Attempts and distinct questions are counted separately on purpose**: three confident wrong answers to one question is one idea stuck, and three across three questions is a weak area, and a single number could not tell those apart. It needs the question bank rather than the revision alone, so a question corrected between two wrong answers still counts as one question. The page says in words that this is evidence of where to look and not a prediction about an exam, which keeps the product's one promise about progress intact (#90).
- An end-to-end browser test of the review loop: be wrong while confident, be told so in words, practise exactly that question, and watch it rest. The unit and integration tests covered each half and the journey between them was untested, which is what the release is for (#87).
- A review screen at `/review`: what is worth revisiting, grouped by topic, with the reason in words rather than a code — "Wrong, and you were sure" instead of `WRONG_WHILE_CONFIDENT`, and a sentence saying why that one deserves the most attention. The order the server sends is the order shown, because the reason is the answer and there is no score to sort by. The empty state separates three situations that would otherwise read identically: nothing is due yet because answers are resting, nothing has been attempted in the topics studied, and nothing at all (#89).
- A session can be started from chosen questions: `POST /api/study/sessions` accepts `revisionIds`, which is how a learner practises exactly what the review queue listed instead of a fresh draw from the topic. Choosing replaces both the selection and the count, and every chosen revision must be published in that topic — choosing is not a way around the eligibility rule, and a revision from elsewhere is refused with `question_not_available`. The same question twice is refused with `duplicate_question` rather than failing on a database constraint. A session belongs to one topic, so practising happens a topic at a time (#89).
- `GET /api/review/queue`: the learner's review queue, derived from their own attempts on read rather than kept as scheduler state, so it is always reproducible from evidence they can already see and there is nothing to drift (ADR 0013). Every item states **why** it is there — `WRONG_WHILE_CONFIDENT`, `WRONG`, `RIGHT_BUT_UNSURE` or `DUE_FOR_RECALL` — as a stable code with the wording left to the client, and the order is the answer rather than a published score. A question answered correctly and confidently rests for a day, doubling with each consecutive confident-correct answer up to 64 days, and any wrong answer resets it. The queue also reports how many questions are waiting and how many were never attempted, so an empty queue can say "nothing is due yet" rather than "nothing to review" (#88).
- The review queue is measured against a budget, which is what makes ADR 0013 honest rather than hopeful. The measurement seeds a history first, because the cost depends on it and a number without the history size means nothing, and **it immediately found a defect**: the first implementation resolved the question behind every attempt one at a time, so cost grew linearly with attempts and the queue was an order of magnitude slower than every other read. Resolving each distinct revision once made it flat — 1408 attempts now cost the same as 610, and p50 at 610 went from 248 ms to 20 ms. Budget 500 ms at the 95th percentile, enforced by CI with 200 seeded attempts (#91).
- `AttemptFact` now carries the revision and the confidence, because a review queue has to know which question was answered and how sure the learner was. Wrong while confident is a misconception rather than a gap, and it is the reason the product asks for confidence at all. `Confidence` moved to the study module's public API for it, and `review` is a new module that may read `study`, `questionbank` and `preparationcatalog` and nothing else.
- Expanded the Java SE 21 (1Z0-830) authorial question pack from 20 to 60 questions, six per topic. The 40 additions are original questions grounded in the Java SE 21 specifications and API documentation rather than copied or derived from third-party practice banks; they remain explicitly unreviewed until a person completes the technical review recorded by the generated packet.
- Expanded the same pack again from 60 to 100 questions, reaching ten questions per topic. The newest 40 remain original, specification-backed drafts; ten include runnable Java 21 verification programs (one per topic) and thirty are conceptual. All 80 post-initial-pack questions remain explicitly unreviewed until a person records a technical review.
- Expanded the Java SE 21 authorial bank from 100 to 150 questions, reaching fifteen per topic. The newest 50 are original specification-backed drafts; twenty include runnable Java 21 verification programs (two per topic) and thirty are conceptual. All 130 questions added after the initial reviewed pack remain explicitly unreviewed.

## [0.1.0] - 2026-10-02

The first release: Study Core. See the [release notes](docs/release/v0.1.0-release-notes.md) for what it does and what it does not.

### Fixed

- Four web tests asserted focus the instant a notice's text appeared, but the focus arrives in an effect, which can be a render later. One of them failed on a loaded CI runner while passing locally. They now wait for the focus, which is the actual requirement: the person ends up on the notice (#13, #14).
- `just --list` showed the wrong description for any recipe with a multi-line comment, because `just` takes the **last** comment line: `scan` was listed as "it means nothing on other systems". The summary is now the last line of each of those blocks, which is what the listing reads.
- Recipe arguments were interpolated into the shell unquoted, so `just import-content a@b.com 'a long password'` passed the password as four separate arguments and the command failed with a policy error that pointed nowhere near the cause. They now go through `quote()`.
- The `justfile` recipes failed on Windows outside Git Bash: `bash` on the PATH there is the WSL launcher, and a WSL distribution has no Docker unless its integration is on, so `just demo` from PowerShell could not reach Docker at all. Git Bash is now named outright for Windows, with the override documented (#15).
- The development `compose.yaml` could not start PostgreSQL at all: it mounted the data volume at `/var/lib/postgresql/data`, which the pinned PostgreSQL 18 image refuses, even on an empty volume. It now mounts at `/var/lib/postgresql`, under a new volume name so a volume written by an older image is left alone rather than reused.
- `deploy/verify-release.sh` asserted exact counts for the rate-limit check, so it only passed against a stack whose throttle bucket was untouched. It now asserts the property that matters, that a forged `X-Forwarded-For` does not get around the limit, which holds whatever the bucket already holds.
- The historical-integrity end-to-end test asserted fixed revision numbers, so it only passed on a fresh database and failed on a second run against the same one. It now states the rule it is really about: exactly one revision is published, it carries the correction, and the revision the learner answered is retired (#15).
- Failures the web framework raises before a controller runs (an unknown path, a method or content type the endpoint does not take, an unacceptable representation) now answer with the same problem body as every other error: a stable `code` and the request id, and none of the framework’s own text. They used to leave both out. Found by the new error inspection (#15).
- Security updates found by the first image scan: Tomcat 11.0.25 (a critical advisory in 11.0.24), Jackson 3.1.7 and 2.21.7 (high advisories), and operating-system package upgrades in both images (#15).
- Built assets are no longer inlined as `data:` URIs, which a strict Content Security Policy blocks; fonts would have failed to load in production (#15).
- Ending a study session early now moves focus to the confirmation and back, instead of leaving keyboard and screen-reader users on a button that had disappeared (#14).
- Flyway now keeps its history table in `public` regardless of the database user name. With the documented user `certforge`, the schema of the same name became the current schema after the first start, so readiness reported the schema as not migrated and the next start failed.

### Added

- A `justfile` of the commands that were scattered through the documentation, grouped and listed by `just` on its own: `just demo` builds and starts the whole thing and publishes ten clearly labelled demo questions, so a fresh installation has something to practise on; plus `up`, `down`, `logs`, `check`, `e2e-release`, `verify`, `baseline`, `rehearse-restore`, `scan` and the content and contract tasks. The demo questions go through the real editorial workflow, with the reviewer separation the release enforces, so seeding also exercises it (#15).
- The Maven wrapper, so `./mvnw` works without Maven installed and pins the version CI uses as well.
- ADR 0010 (**proposed**, awaiting a decision): the arrangement for the first deployment, written as recommendations with their reasoning so it can be accepted or changed: TLS terminated in front of the web container, one backend instance until rate limiting has a shared store, daily off-host backups kept 30 days and restored for real quarterly, and stated recovery objectives of 24 hours of data and one working day to be back (#15).
- Catalog inspection in the editorial desk, for administrators: tracks, exam versions and the topics mapped to each with their objective wording, plus a plain statement of what can be published where, since publishing binds a revision to the active exam version of its topic and to that exam's Java release. Read-only, because in this release the catalog is created by migration (#14).
- Keyboard and screen-reader checks in CI: every screen is walked with Tab (each control reachable, a visible focus ring on each, the skip link first and working, a confirmation that takes the focus and gives it back), and the accessibility tree of the main screens, which is what a screen reader announces, is asserted. What a person still has to judge is now narrower and is written down in the demonstration scripts (#13, #14, #15).
- The content pack build now checks that the answer key agrees with what the code does: when an option carries the text the program prints, that option must be the one marked correct. It verified the program and the key separately before, so a question could print one thing and mark another as the answer (#8).
- Accessibility checks now cover **both colour schemes** (axe runs once per scheme on every page the end-to-end suite visits, measuring with reduced motion so it does not sample the 150 ms colour transition) and WCAG 2.1 reflow: no page may need sideways scrolling down to a 320 pixel width (#13, #14, #15).
- A content review packet for the initial question pack, generated from it (`content/build-review-packet.mjs`): each question as the learner sees it, the answer key, reasons and references, the output the build verified, and the content-policy checks as boxes to tick. CI fails if it is out of date (#8, #15).
- The technical review of the initial question pack, done on 2026-10-02, is recorded in `content/java-se-21/review.json` with the reviewer, the date, the method and what the review does not establish. Each reviewed question carries a digest of the text a reviewer judges — the prompt with its code, the options, the answer key, the explanations, the rationale and the references — and a second one of the output the build proved, so **a question edited later counts as unreviewed again** instead of inheriting the verdict: the packet marks it, and because CI compares the committed packet with a fresh build, it cannot reach `main` still claiming the old review. The two digests are weighed differently on purpose. Changing the text, making the program print something else, or deleting the program all lose the review. **Writing a program for a question that had none keeps it**, and is noted as better supported than when the verdict was given: nothing the reviewer read changed and the claim now has a program behind it, so folding the two together would have marked a question unreviewed for being verified — punishing the exact move ADR 0011 wants to encourage. Reformatting the JSON changes nothing either, because the digest covers what was read, not how the file was written (#8).
- The content pack build can verify a **module graph**, not only a flat set of sources. A question with a `modules/` directory is compiled with `--module-source-path` and run with `--module`, with the single `Main.java` under it naming the entry point. Some claims are only true of modules — whether `requires transitive` makes a dependency readable, what `exports` and `opens` each permit — and flat compilation on the class path cannot show any of them, so those questions had no mechanical backing at all.
- `t07-requires-transitive` is no longer conceptual: it carries three modules where `app` requires only `lib`, uses a type from `util`, and compiles because `lib` declares `requires transitive util`. Remove the `transitive` and the build fails with `package u is not visible`, so the verification establishes the answer rather than decorating it. It kept its recorded review, which is the split digest doing its job. Three questions now carry nothing mechanical instead of four, and the review packet derives that list rather than repeating it, so it cannot go stale again.
- The review packet now shows the program behind a question whose code the learner never sees, because a reviewer cannot judge whether a proof is a proof without reading it, and marks in the question table whether the verified code is shown or hidden (#8).
- References in the question pack are now checked against the three sources that are allowed to be one — the Java SE specifications, the API documentation and JEPs — and the two that are versioned must be scoped to the question's declared release. The only previous check was the `https://` prefix, which a dead link, a blog post or the Java 17 page all satisfy, while the content policy asks for references "sufficient for independent verification" and ADR 0005 forbids fabricating them. Proven to fail on all three: wrong release in the API URL, wrong specification version, and an unofficial site. What no check can do is tell whether a reference supports the claim; that stays with the reviewer (#8).
- ADR 0012 (**proposed**, awaiting a decision): translate the interface to Brazilian Portuguese and keep the question text in English. The product's language had never been decided anywhere — the app is English only by drift, while the documentation is deliberately bilingual. The reasoning for the split is that the exam is sat in English and its wording precision is part of what it tests, a translated question is new content needing its own review rather than a copy, and the references are English and normative. It also records the cost, which is not the strings: 97 browser assertions and the unit tests find elements by their English accessible name, and those names are the accessibility guarantee, so translating means reworking the suites that are the release's evidence — hence not in `v0.1.0`. #74 carries the plan.
- ADR 0011 (**proposed**, awaiting a decision): grade each question by the evidence behind it, so the human review asks only what the machine cannot supply. Seventeen of the twenty questions carry a program the build runs and checks against the answer key; three carry nothing mechanical, and ADR 0005 asks the same undifferentiated review of both. It also records what was rejected and why, including letting an official reference stand in for human review — which would exempt exactly the questions with the least evidence — and using licensed practice material as an answer key, which is both not ours to derive from and a weaker source than the specification and the compiler.
- `content/private/`, ignored by git, for study material a maintainer holds a licence to but no right to redistribute. CI fails if any file under it is ever tracked, because `.gitignore` only asks and a `git add -f` or a stray `git add -A` gets past it. This repository is public and Apache-2.0, so a file committed under `content/` is not merely published but sublicensed to everyone who clones it. The content policy now says what it governs — published content — and the authoring guide covers the two ways this leaks anyway: committed screenshots captured from a running stack, and writing your own version of someone else's question into the authorial pack, which is derivation and which no test can catch.
- `just publish-content` takes the reviewed question pack through the real editorial workflow — create, submit, approve, publish — carrying the recorded verdict as the approval comment and the record's `checklist` as what the reviewer attests to, and `just reviewer` creates the second account approval needs. It automates the typing, not the judgement: a question whose recorded digest no longer matches is **held back** rather than published, and the reviewer account is never invented, because a reviewer this script made up would be a lie in the provenance of real content. It also refuses a reviewer that is the author and skips prompts already in the bank, so a second run tops up instead of duplicating (#8, #15).
- Release documentation: demonstration scripts for the learner and editorial journeys with screenshots (and a script for what only a person can check), draft release notes, a readiness review that maps each acceptance criterion of #15 to its evidence and lists the blockers, a threat model brought up to date with what was built and found, and backup, rollback, reconciliation and incident-response procedures in the operations guide, the first two exercised in CI (#15).
- Release gates in CI: a performance baseline with budgets (one learner, sequential, plus backend startup), a backup and restore rehearsal that compares every table, a bundle size budget, `npm audit`, secret scanning of the whole history (gitleaks) and CodeQL for the backend and the web app; and a migration upgrade test that keeps a reviewed revision across the latest change (#15).
- Release validation that runs in CI: an authorization matrix generated from the application’s own request mappings (an endpoint without an access rule fails; each role is refused what it lacks and admitted to what it has; state-changing endpoints refuse a missing CSRF token), an answer-privacy journey in a real browser (responses, page, storage, cache headers, direct API access, built bundle), a historical-integrity journey (an answer keeps showing the revision the learner saw after the question is replaced), and an inspection of errors, metrics and logs of the running stack (#15).
- A release-like environment: backend and web images, an nginx proxy with a strict Content Security Policy and security headers, PostgreSQL, and a `release` CI job that scans the images, checks the proxy (including that a forged `X-Forwarded-For` cannot get around rate limiting) and runs the whole end-to-end suite against the images (#15).
- Editorial history by name: the editorial view of a question now says who wrote, reviewed and published each revision (by email address, staff-only endpoints). A review records the content-policy checklist items the reviewer ticked (`checklist`, optional, fixed codes, migration V11); it is shown in the review notes and does not gate approval. The web app uses both (#14).
- Comparison of a revision with the one before it (word by word, field by field, announced in words as well as marked) and protection of unsaved edits in the question editor, by link, back button or closing the tab (#14).
- Review and publication in the web app: a reviewer reads the question as the learner will see it and approves it or sends it back with a comment; an administrator publishes (after a confirmation) or retires a revision; an author starts a new revision of a published question. Covered end to end by a test that takes one question from draft to published through three accounts (#14).
- Editorial desk in the web app: question queue with status filters, the draft editor (save unfinished work, send for review with a list of what is missing that links to each field), and a read-only revision view that shows the question as the learner will see it before the answer key. Staff-only, shown by permission (#14).
- A shared visual system (editorial desk look, light and dark tokens, bundled fonts) applied to the whole web app, and fenced code blocks in questions now render as code for learners and reviewers. See the web interface guidelines (#14).
- Learner history, session review and topic progress pages, and end-to-end tests with Playwright and axe on desktop and mobile viewports, run in CI against the real backend and PostgreSQL (#13).
- Learner study flow in the web app: start a practice session from a topic, resume the one in progress, single and multiple choice questions with confidence, idempotent submission with feedback, explanation and references, finish or end a session, and expired-session states, with focus managed across questions and results (#13).
