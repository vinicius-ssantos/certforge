## What the validation found

Running the real images behind the real proxy found problems the earlier tests could not. All are fixed and now guarded:

- Critical and high advisories in Tomcat and Jackson, as managed by Spring Boot 4.1.1, plus outdated operating-system packages in both images.
- The strict Content Security Policy would have blocked the app's fonts in production, because the build inlined them as `data:` URIs.
- Behind a proxy every user would have shared one rate-limit bucket, and a proxy that appended to `X-Forwarded-For` would have let a client choose its own address.
- Errors the web framework raises before a controller runs (unknown path, wrong method or content type) had no stable code and no request id.
- Flyway looked for its history table in the wrong schema when the database user is named `certforge`, as in the documented setup: readiness reported `DOWN`, and the next start failed. (Found earlier, in #13.)

## Performance baseline

Measured on 2026-10-01 with `deploy/measure-baseline.mjs`: one learner, sequential requests through the nginx proxy, 30 rounds, backend and PostgreSQL in Docker Desktop on a developer laptop, Java 25. **This is a baseline for noticing regressions, not a statement about capacity.**

| Flow | p50 (ms) | p95 (ms) | Budget p95 (ms) |
|---|---:|---:|---:|
| sign in | 58 | 64 | 1500 |
| list tracks | 7 | 10 | 400 |
| start session | 16 | 20 | 600 |
| read session | 8 | 11 | 400 |
| submit answer | 11 | 16 | 600 |
| finish session | 9 | 12 | 600 |
| read history | 8 | 12 | 500 |
| read progress | 8 | 13 | 500 |

Backend startup 6.6 s (budget 30 s). Web app on first load: JavaScript 125 KB and CSS 4 KB, gzip-compressed (budgets 170 KB and 12 KB). The budgets are several times the baseline so a slow shared runner does not fail them and a real regression does; CI enforces all of them.

## Gates that run on every change

Backend: build, formatting, PMD, 150 integration tests on PostgreSQL. Web: lint with accessibility rules, strict type checking, unit tests, a production build, a size budget, `npm audit`. End to end: the Playwright suite twice, once on the dev server and once on the release images. Release images: vulnerability scan, proxy and header checks, restore rehearsal, performance budgets, privacy inspection. Repository: secret scan of the whole history, CodeQL for Java and TypeScript, Dependabot.

## Blockers

These need a person. None can be closed by more automation.

1. **Verify the exam objective wording against Oracle's page (#68).** The topic names and objective wording seeded by `V4__seed_java_certification_catalog.sql` come partly from secondary summaries, because Oracle's exam page is rendered by JavaScript and refuses automated clients; three lines in particular need a human to compare them in a browser. The catalog screen lists the wording for the active exam version, topic by topic, which is the easiest place to do it. This is a gate on publishing in the track, not on the questions themselves.

   The questions were reviewed: on 2026-10-02 the project owner read all twenty in the [content review packet](content-review-packet.md) and reported no technical errors, recorded in [`content/java-se-21/review.json`](../../content/java-se-21/review.json). That record keeps digests of each reviewed question, so editing one afterwards makes it count as unreviewed again rather than inheriting the verdict, while writing a program for one that had none keeps the verdict. What the review does not establish is listed in the packet: the reviewer is the project owner rather than an independent third party, and three questions have no runnable code, so nothing mechanical backs them up.
2. **Manual accessibility review (#13, #14).** Following Script C of the [demonstration scripts](demo-scripts.md). Automated checks now cover contrast in both colour schemes, reflow down to 320 pixels, every control being reachable by Tab with a visible focus ring, and the accessibility tree a screen reader reads from. What is left is what a machine cannot judge: whether the tab order makes sense, whether status messages are actually announced and in a sensible order, and whether the dark and zoomed layouts are comfortable.
3. **A first human walkthrough.** Someone other than the author follows Scripts A and B in the [demonstration scripts](demo-scripts.md) and says whether it makes sense.
4. **Decisions for the first deployment** (not code): who terminates TLS, how often backups run and where they are kept, and the recovery objectives. [ADR 0010](../adr/0010-first-deployment-posture.md) proposes an answer to each, with the reasoning, so this is now a decision to accept or change rather than a blank page.

## To release once the blockers are closed

1. Close #13, #14, #68 and #15, then the epic #2 and the milestone. (#8 closed on 2026-10-02 with the recorded review.)
2. Publish the pack on the instance that will serve it: `just reviewer <email> <password>` once, then `just publish-content <email> <password>`. That walks the real editorial workflow and carries the recorded verdict, holding back anything the review no longer covers. The recorded review is the technical judgement; the editorial desk is where it becomes a published revision with author and reviewer provenance. Until that happens a fresh install has no questions.
3. Set the version: `0.1.0-SNAPSHOT` to `0.1.0` in `pom.xml` (the web app is already `0.1.0`), and `[Unreleased]` to `[0.1.0]` in the changelog.
4. Turn the [release notes](v0.1.0-release-notes.md) from a draft into the final text, with the date.
5. Tag `v0.1.0` on the commit whose CI is green, and create the GitHub release from the notes.
