## What the validation found

Running the real images behind the real proxy found problems the earlier tests could not. All are fixed and now guarded:

- Critical and high advisories in Tomcat and Jackson, as managed by Spring Boot 4.1.1, plus outdated operating-system packages in both images.
- The strict Content Security Policy would have blocked the app's fonts in production, because the build inlined them as `data:` URIs.
- Behind a proxy every user would have shared one rate-limit bucket, and a proxy that appended to `X-Forwarded-For` would have let a client choose its own address.
- Errors the web framework raises before a controller runs (unknown path, wrong method or content type) had no stable code and no request id.
- Flyway looked for its history table in the wrong schema when the database user is named `certforge`, as in the documented setup: readiness reported `DOWN`, and the next start failed. (Found earlier, in #13.)

## Performance baseline

Measured on 2026-10-01 with `deploy/measure-baseline.mjs`: one learner, sequential requests through the nginx proxy, 30 rounds, backend and PostgreSQL in Docker Desktop on a developer laptop, Java 25. **This is a baseline for noticing regressions, not a statement about capacity.**

| Flow | p50 (ms) | p95 (ms) | Budget p95 (ms) |
|---|---:|---:|---:|
| sign in | 58 | 64 | 1500 |
| list tracks | 7 | 10 | 400 |
| start session | 16 | 20 | 600 |
| read session | 8 | 11 | 400 |
| submit answer | 11 | 16 | 600 |
| finish session | 9 | 12 | 600 |
| read history | 8 | 12 | 500 |
| read progress | 8 | 13 | 500 |

Backend startup 6.6 s (budget 30 s). Web app on first load: JavaScript 125 KB and CSS 4 KB, gzip-compressed (budgets 170 KB and 12 KB). The budgets are several times the baseline so a slow shared runner does not fail them and a real regression does; CI enforces all of them.

## Gates that run on every change

Backend: build, formatting, PMD, 150 integration tests on PostgreSQL. Web: lint with accessibility rules, strict type checking, unit tests, a production build, a size budget, `npm audit`. End to end: the Playwright suite twice, once on the dev server and once on the release images. Release images: vulnerability scan, proxy and header checks, restore rehearsal, performance budgets, privacy inspection. Repository: secret scan of the whole history, CodeQL for Java and TypeScript, Dependabot.

## What a person checked

These could not be closed by more automation. All were done on 2026-10-02 by the project owner.

1. **The content pack (#8).** All twenty questions read in the [content review packet](content-review-packet.md), with no technical errors reported, recorded in [`content/java-se-21/review.json`](../../content/java-se-21/review.json). That record keeps digests of each reviewed question, so editing one afterwards makes it count as unreviewed again rather than inheriting the verdict, while writing a program for one that had none keeps it. What the review does not establish is listed in the packet: the reviewer is the project owner rather than an independent third party, and three questions have no runnable code, so nothing mechanical backs them up.
2. **The exam objective wording (#68).** Compared with Oracle's [exam page](https://education.oracle.com/java-se-21-developer-professional/pexam_1Z0-830) in a browser and reported to match, including the three lines the secondary summaries disagreed about. No migration was needed. The page refuses automated clients, so nothing re-checks this: it is a match as of 2026-10-02, to be compared again when Oracle revises the exam.
3. **Manual accessibility review (#13, #14).** Script C of the [demonstration scripts](demo-scripts.md), covering what a machine cannot judge: whether the tab order makes sense, whether status messages are announced and in a sensible order, and whether the dark and zoomed layouts are comfortable. Nothing to correct was reported. Automated checks continue to cover contrast in both colour schemes, reflow to 320 pixels, Tab reachability with a visible focus ring, and the accessibility tree.
4. **The first walkthrough.** Scripts A and B, against an instance with the real pack published rather than demo data, which `just publish-content` made possible. Nothing to correct was reported.
5. **The first-deployment decisions.** [ADR 0010](../adr/0010-first-deployment-posture.md) accepted as written, along with [ADR 0011](../adr/0011-grade-content-evidence.md) and [ADR 0012](../adr/0012-interface-language.md).

### What that does not amount to

- **One person, who is also the author.** The walkthrough was originally written as "someone other than the author follows Scripts A and B", and that stronger form was not met: the same person wrote the project, reviewed the content and did the walkthrough. A second pair of eyes remains the most valuable thing this release has not had.
- **Accepting ADR 0010 is not deploying to it.** TLS termination, off-host backups and the recovery objectives are decided; a deployment still has to be built to match, and the [operations guide](../engineering/operations.md) says how.
- **Nothing is published until someone publishes it.** A fresh install has no questions; `just reviewer` and `just publish-content` take the reviewed pack through the editorial workflow on the instance that will serve it.
