# v0.4.0 — Code Analysis gap audit (18 November 2026)

Status: **read-only code/content audit** for the proposed OpenSpec change `v04-code-analysis-learning`. This is not a content approval, release tag or user acceptance.

## Reproducible inventory

Source: `content/java-se-21/*/question.json`, `Main.java` / `modules/`, and `expected.txt`, checked by a repository-local PowerShell/JSON inventory.

| Measure | Observed |
| --- | ---: |
| Java SE 21 question directories | 150 |

| Main explanations missing/blank | 0 |

**Interpretation:** 106/150 question prompts do not contain a fenced code block; this alone is **not a defect**. Many ask about a short expression or a conceptual rule. Fixed proof sources are stored separately and need not appear verbatim in the prompt. This inventory does not evaluate explanation accuracy, option plausibility or human editorial approval.

These six JSON and evidence files were read, but **their correctness and editorial acceptances were not formally approved**. An owner-selected pilot must still undergo the established review workflow.

## Feedback delivery comparison

| Behavior | Practice | Timed mock active | Timed mock terminal |
| --- | --- | --- | --- |
| Fixed question prompt and answer options | Yes | Yes | Yes |
| Correct answer, full option rationales and main explanation | After accepted answer (`AnswerFeedback`, `AnswerList`) | **No**, suppressed in `MockExamPage` and backed by server disclosure boundary | Yes (`MockExamResultPage.QuestionReview`) |
| Verified source files and recorded expected output | **Yes**, `VerificationEvidence` inside `AnswerFeedback` | **No** (correctly unavailable) | **Missing in current UI**, although `MockExamViews.Answer.verification`, `MockExamService.verificationOf` and the generated TypeScript `Answer` schema already carry the data |
| Keyboard-readable, CSP-safe source presentation | `Prompt` and `VerificationEvidence` | `Prompt` | `Prompt`; verification block missing |

**Concrete gap (candidate implementation):** reuse `VerificationEvidence` in the *terminal* `QuestionReview` after `AnswerList`, exactly where the accepted practice feedback shows it. Do **not** add it to the active mock page. No API, database or schema change is needed.

**Accessibility follow-up:** `VerificationEvidence` currently renders a fixed `id="verified-heading"`. A mock result can expand multiple questions simultaneously. Give each instance a unique heading ID (e.g., React `useId()`) to avoid duplicate IDs and retain `aria-labelledby`.

## Recommended narrow acceptance test

1. Active timed mock: fixed source may appear in the question, but output, correct options and explanation do not appear before terminal status. Preserve existing tests and add a dedicated negative assertion if useful.
2. Completed/expired mock: expanding a question with `answer.verification` reveals named fixed files, expected recorded output, main explanation and option rationales, with no live execution.
3. Completed mock with multiple expanded code reviews: no duplicated ID for verification headings, and every code/output block is keyboard reachable.
4. Question without verification: no empty or misleading verification panel. Never infer “editorially approved” from a compiler proof.
5. Desktop and narrow mobile: code remains readable through wrapping/scroll; tests, CSP and safety checks remain green.
6. Any change to question explanations requires the existing human editorial acceptance flow. No bulk rewrite.

## Decision required

The owner should approve whether the minimal v0.4.0 pilot is **terminal mock evidence parity + a small reviewed explanation-quality sample**, or whether additional explanation UI is worth adding. The proposed UI fix is independently testable and may be prepared in a **draft PR**, but it must not be silently merged or treated as a release decision without that approval.
