# `v0.3.0` scope proposal

- **Status: a proposal.** Nothing here is decided, nothing is tagged, and no part of it has been accepted. It is written to be disagreed with on the merits by the project owner, who decides.
- Date: 2026-10-07. Head is `f02bcfe`, 26 commits after `v0.2.0` (`2f47640`, 2026-10-03).

## What this document is for

The [roadmap](../roadmap/releases.md) says `v0.3.0` is **Mock Exams**, with the outcome *"A learner completes timed simulations and receives a blueprint-based weakness report."* The roadmap also says each release must create a demonstrable user outcome, and that later releases remain hypotheses until the preceding one is used and reviewed.

This document checks the hypothesis against the tree. It reaches three conclusions that need a decision:

1. The mock exam blueprint is unverified (#113), and the release's headline claim is about the shape of a real exam. [What to do about that](#the-decision-that-blocks-this-113).
2. **The mock exam cannot be started on any installation this project's own tooling can produce.** This is not filed as an issue and it is a larger blocker than #113. [Why](#the-blocker-that-is-not-filed-the-mock-cannot-start).
3. The 26 commits are not mostly mock exams. [A name for what is actually here](#is-this-release-mock-exams).

### What a learner would notice

**A timed mock exam, end to end.** `/api/study/mock-exams` was in the `v0.2.0` tree and unreachable on purpose; #108 gives it a runner — server-backed countdown, direct question navigation, answered state, browser-local review flags, an irreversible submit that names the unanswered questions — and a result screen with the practice score, elapsed time, named topic breakdown and full answer review. #111 adds mock history as its own read model: an active run exposes participation only, a terminal run exposes score and per-topic evidence, topics below that run's practice target are marked, and none of it touches ordinary topic progress or the adaptive-review queue. #124 fixed a real accessibility defect found on the way: the heading was split across nodes, so focus was dropped.

That is the roadmap's outcome, in the product, modulo the two blockers below.

**The whole interface in Brazilian Portuguese.** Carries out [ADR 0012](../adr/0012-interface-language.md). It follows the browser's preferred language, a labelled switcher overrides it, the choice is remembered in the browser; no schema change, no account setting. Question text stays in English deliberately — the exam is sat in English, and a translated question is new content needing its own technical review. Because the two languages now sit on one screen, every English island carries `lang="en"` and `<html lang>` follows the choice, so a screen reader does not read English with Portuguese phonetics. Counts go through `Intl.PluralRules`, which matters: CLDR puts Brazilian Portuguese's singular at zero *and* one, so "0 questão" is right and "0 questões" is not.

This is the largest learner-visible change in the 26 commits, and the roadmap did not ask for it.

### What a learner would not notice

**The content pack is now fully proved by the build.** 150 of 150 questions carry a program the build compiles for Java 21, runs, and checks prints exactly what the question claims, with the option carrying that output being the one marked correct. At the tag it was 69. The last to fall were the hardest: the module system (a claim about modules is not true of a flat set of sources), and concurrency, I/O and localisation, where a careless program would have been platform-dependent rather than wrong. Several questions are proved by *not* compiling, pinned to the diagnostic the compiler actually reports.

**This is not human review, and must never be described as if it were.** [ADR 0011](../adr/0011-grade-content-evidence.md) is explicit: the build establishes the answer key mechanically, and what remains for a person is what a machine cannot judge — one defensible interpretation, plausible distractors, complete explanations, accessible prose. 130 of 150 questions still have no recorded human review (#80). What changed is that every one of them is now **Verified** rather than **Asserted**, which lowers the cost of the review that is still owed. It does not discharge it.

**The interview track foundation.** All eight decisions of [ADR 0016](../adr/0016-interview-track-taxonomy.md) are implemented. `catalog_exam_version` became `catalog_track_version` with the exam-specific columns moved out (V13, a rename over live data); the twelve-topic Java Backend taxonomy is seeded as a DRAFT track and DRAFT version (V14); content rules are conditional on track kind, so an interview question is not refused for stating no Java release; per-question seniority exists and is required on an interview track and refused on a certification one (V15); and the editorial desk got its own catalog endpoint, because seeding a draft track had made it reachable by nobody — the question editor was reading the learner endpoint, which serves only active tracks.

**It has no content and no learner can see it.** Both rows are DRAFT, publishing requires an active track and version, and activating them is a deliberate act for when there is something to serve. #20 — the first reviewed interview content pack — is open and untouched. The structure is complete; the track is empty.

**Everything else.** Every interface string moved into a typed catalog (#122), which is what made #123 possible. The deploy scripts now explain a failed administrator sign-in instead of printing a stack trace (#110, which landed before the tag was cut and was already in the `v0.2.0` notes). Four dependency bumps.

## The decision that blocks this: #113

The blueprint states three things about Oracle's exam — **50 questions, 120 minutes, 68% to pass** — and nothing in this repository records where they came from or a date on which a person checked them. They are in `MockExamBlueprintCatalog`, [ADR 0015](../adr/0015-separate-mock-exam-aggregate.md) and the [mock exams document](../architecture/mock-exams.md). Oracle's exam page is rendered by JavaScript, refuses automated clients, and was down for maintenance when last tried.

What already exists in mitigation: the learner-facing copy calls it a "practice target" and says "the practice target is for study guidance and is not an Oracle score prediction"; the track page says "the current CertForge blueprint controls the question count, duration and practice target"; the architecture document carries a blockquote saying the three numbers are unverified; and ADR 0015 is careful to call the five-per-topic distribution a CertForge choice rather than an Oracle weighting.

What is not mitigated: the three numbers themselves are claims about Oracle's exam, and they carry no caveat on the screen a learner practises on. **A learner practising a 50-question, 120-minute run calibrates their pacing to it.** Being wrong here trains the wrong rhythm, which is worse than being quietly unhelpful.

### The options, and what each costs

**A. Ship, with the limitation stated prominently in the release notes.**

Cost: a release note is not where a learner reads anything. The misleading claim, if it is one, lives on the exam screen and in the countdown; the correction would live in a document nobody studying opens. It also inverts this project's own standard — `v0.2.0` deliberately held the mock exam screen out of the tag because nobody had checked it, rather than shipping it with a note. Cheapest option; weakest honesty for the specific risk.

**B. Ship, having first changed the product so it stops implying a specific exam format.**

Cost: a wording change in `web/src/i18n/en.ts` and `pt-BR.ts`, the mock exam and track screens, the architecture document and an ADR 0015 amendment. Perhaps a day. The real cost is to the product: a mock exam whose length and clock are presented as arbitrary CertForge choices loses most of what a mock exam is for, which is rehearsing a specific pacing. And the claim has to be re-made later, when the check succeeds, which means the wording changes twice.

**C. Hold the release until #113 is verified, with no known date.**

Cost: 14,000 lines of finished work — including a full Portuguese interface and a content pack that took five commits to prove — sit behind the uptime of a third-party web page. "No known date" is the honest description and it is also the problem: the roadmap's release policy exists so that work reaches a user, and this trades all of it against one unknown. It also over-reads the difficulty: #113 is not research. It is one person opening one URL in a browser, with three values to compare.

**D. Recommended: treat #113 as blocking the *claim*, not the *code*, and decide it with a rule rather than a coin flip.**

Before tagging, a person opens <https://education.oracle.com/java-se-21-developer-professional/pexam_1Z0-830> in a browser and attempts the check. Then:

- **It matches.** Record the date in ADR 0015 and the mock exams document, as a match *as of that date* rather than a property anything keeps true, drop the unverified caveat, ship. This is the outcome worth a few retries over several days.
- **It differs.** Correct `MockExamBlueprintCatalog`, and say so in the release notes, because anyone who already practised against the old shape practised the wrong one. #113's acceptance criteria already require this.
- **The page is still unreachable at tag time.** Apply the *minimal* form of option B: in the learner-facing copy only, stop presenting the three numbers as the shape of Oracle's exam and present them as CertForge's practice blueprint — which is what the architecture document and the track page already call them. Keep the numbers. Ship. Then #113 stays open against the stronger claim, and taking it back is a wording change rather than a redesign.

Reasoning: the question is not "is it safe to ship an unverified number" but "where does the unverified claim appear". A claim a learner acts on must be either verified or not made, and a release note cannot satisfy either. But the gap between "verified" and "not made" is a few hours of copy, not a held release — so there is no version of this where C is the right trade.

Cost of D, stated plainly: it asks for a person's attention on a specific day, twice if the page is down, and it may force the copy change anyway. It is more work than A and less honest than C would be if Oracle's page were permanently gone, which it is not.

**A note #113 already makes, worth repeating in the release plan:** a blueprint is per exam code and nothing inherits another exam's timing, so this check must be repeated for every exam version ever added.

## The blocker that is not filed: the mock cannot start

This was found while reading the tree for this proposal and is **not** tracked by any open issue.

- The blueprint is `new MockExamBlueprint("1Z0-830", 50, Duration.ofMinutes(120), 68, 5)` over 10 top-level topics: **5 published questions in every one of the ten topics, or 50 in total.**
- `MockExamPlanner` refuses rather than shortening or rebalancing: fewer than five eligible questions in any topic throws `insufficient_mock_content`. The architecture document says this is deliberate, and it is right.
- `deploy/publish-pack.mjs` publishes only questions that are both reviewed and `APPROVED` in `content/java-se-21/review.json`, and refuses a question whose digest has changed since review. There are **20 such questions: exactly 2 per topic.**
- `deploy/seed-demo.mjs` seeds one topic only, and says its questions are throwaway demo data.

So on a fresh installation prepared with this project's own tooling, every attempt to start a mock exam fails with `insufficient_mock_content`. The runner, the countdown, the delayed-feedback rule, the result screen and the weak-topic report are all finished and all unreachable — the same state `v0.2.0` recorded for the API, one layer higher up.

This is strictly larger than #113. An unverified blueprint misleads a learner who can run a mock; this one means nobody can. Against the roadmap's gate *"its documented user journey is demonstrable"*, it is the release's actual blocker.

**It is bounded, which is the good news.** Five per topic needs 3 more reviewed questions per topic — **30 of the 130 unreviewed questions**, chosen as three per topic rather than by convenience. Every one of them is now **Verified** rather than Asserted, so what a reviewer owes each is judgement on interpretation, distractors, explanations and accessible prose, not re-deriving the answer key. That is the cheapest 30 questions this pack will ever have, and it is a direct down payment on #80.

The alternative — publishing unreviewed questions to make the mock startable — must not be done. It would put a review on the provenance of content nobody read, which is the one thing `publish-pack.mjs` exists to refuse.

Recommendation: file this as an issue, make it release-blocking, and put the 30-question review in the release's scope. If the owner would rather not, the honest fallback is to ship with the mock exam screen reachable but documented as unusable without 50 published questions — which would be the second release in a row to ship this feature as unreachable, and is worth refusing on those grounds alone.

## Is this release "Mock Exams"?

Counted by what a learner can newly do, the release has two headline features, not one:

- a timed mock exam with a weakness report — the roadmap's `v0.3.0`;
- the entire interface in Brazilian Portuguese — on no roadmap at all, and the change most learners would notice first.

Counted by effort, the largest single body of work is neither: it is finishing the content pack's mechanical proof, 81 questions across five commits, plus the interview track foundation across seven.

The roadmap is a hypothesis and this project revises one when the evidence changes. The evidence here is that "Mock Exams" names about a third of the release, and names the third with two open blockers.

### Proposed name

> **`v0.3.0` — Mock Exams and Portuguese**
>
> **Outcome:** A learner completes a timed, blueprint-based simulation, receives a per-topic weakness report for that run, and uses the whole interface in Brazilian Portuguese or English.

Why this and not the alternatives:

- **Keep "Mock Exams" alone.** Accurate about the roadmap, inaccurate about the release: it would omit the change a learner meets on the first screen, and leave the Portuguese interface as a line in a changelog.
- **Rename to "Portuguese", deferring mock exams to `v0.4.0`.** Defensible if the owner judges the two blockers unfixable in this cycle — and it is the honest name in that case, because an unstartable mock exam is not an outcome. It costs the roadmap a renumbering of everything downstream, and it would shelve finished work for a second release.
- **Name it for the content pack.** Rejected: "every question is now proved by the build" is real and it is invisible to a learner. Under the release policy that is an internal implementation slice, not a product outcome.

The interview track is deliberately absent from the name. It has no content, no learner surface, and naming it would promise something the tree does not contain.

## Proposed scope

### In

**Mock exams** — the timed runner, server-owned deadline, direct navigation, browser-local flags, irreversible submit naming the unanswered; the result screen with practice score, elapsed time, named topic breakdown and full post-close review; mock history as its own read model with weak-topic markers that do not feed ordinary progress; the delayed-feedback server rule.

**Interface language** — Portuguese and English, browser-preferred default, remembered switcher, per-island `lang`, locale-correct dates and plurals; question text in English in both.

**Content** — the pack's 150 questions each carrying a program the build runs, and **30 newly human-reviewed questions, three per topic**, which is what makes a mock exam startable.

**Carried, not claimed** — the interview track foundation and the editorial catalog view ship in the tag because they are in the tree and are sound; they are not part of the outcome and the release notes must say so.

### Out

Interview content and any learner-facing interview surface (#17 and children). Any readiness, mastery or predicted-score claim. A review queue spanning topics in one sitting. Code execution. A second interview or certification track. Mock exams for any exam code other than `1Z0-830`.

## Acceptance criteria

- On an installation prepared only with `deploy/publish-pack.mjs`, a learner can start, complete and review a 50-question mock exam. **This is the criterion that fails today.**
- No endpoint returns correctness, answer keys, option flags, explanations or references while a run is `IN_PROGRESS`; the OpenAPI contract test keeps active-run schemas from growing answer material.
- A started run never gains a newly published question and never swaps a deprecated revision; the exact revision the learner saw is recoverable after close.
- The score denominator is the blueprint's full question count; unanswered items count as misses rather than disappearing.
- A second start for the same learner and track conflicts with the existing session id rather than replacing its snapshot or deadline.
- Mock evidence does not alter `attempted`, `correct`, confidence-based review evidence or the adaptive-review queue.
- Either the three blueprint numbers are recorded as checked against Oracle's page on a stated date, or no learner-facing screen presents them as the shape of Oracle's exam.
- The mock runner and result screens pass automated accessibility checks in both colour schemes and both languages, and a person has walked the run keyboard-only.
- Every learner-facing string renders in both languages with no missing key, and `<html lang>` and the English islands are correct on the mock screens.
- V13's rename over live data has a documented rollback consideration.

## What this does not amount to

- **130 of 150 questions are unreviewed by a human, and "proved by the build" is not a review.** The build establishes the answer key and nothing else: not wording, not ambiguity, not whether the question tests the objective, not the quality of an explanation. If the 30 reviews proposed above are done, it becomes 100 of 150 unreviewed. Nothing here claims the pack is reviewed content.
- **Every review in this pack is by one person, who is also its author.** The same limitation `v0.1.0` and `v0.2.0` recorded. A second, independent reviewer would be stronger evidence and does not exist.
- **The Portuguese wording had one native-speaker read, by the project's own author, on 2026-10-04.** That is the author reviewing their own project's translation. No independent speaker has read it, nobody has used it to study, and no screen-reader user has heard it.
- **The interview track is empty.** Twelve topics, a draft taxonomy version, conditional content rules and a seniority field, with zero questions. The structure being complete is not the track existing for anyone. The seniority taxonomy and the twelve-topic boundary are editorial judgements about the market, stated as such in V14, not measurements.
- **The blueprint's five-per-topic distribution is a CertForge practice choice**, not an Oracle-published objective weighting, and ADR 0015 already says so.
- **A mock result describes that run.** It is not a readiness forecast, a mastery claim or a probability of passing the real exam, here or anywhere.
- **Nobody has studied with any of it.** Not the recall rule from `v0.2.0`, not the mock exam, not the Portuguese interface.
- **No mock exam has been exercised in a browser end to end.** `web/src/mock/` has component tests including axe, and `web/e2e/` has no mock exam spec at all. Every other learner journey in this project has one.
- Everything `v0.1.0` and `v0.2.0` listed still applies: one backend instance, no TLS in the images, no email verification or password reset, no tracing.
