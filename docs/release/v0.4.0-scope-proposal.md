# `v0.4.0` scope proposal

- **Status: a proposal.** Nothing here is decided, nothing is tagged, and no part of it has been accepted. It is written to be disagreed with on the merits by the project owner, who decides.
- Date: 2026-11-15. Head is `2f6ce4e`, 6 commits after `v0.3.0` (`v0.3.0` tag).

## What this document is for

The [roadmap](../roadmap/releases.md) says `v0.4.0` is **Code Analysis**, with the outcome *"A learner practices questions about compilation, runtime behavior, and program output with high-quality code presentation. This release still uses prevalidated content and does not require arbitrary execution."*

Unlike [`v0.3.0`'s scope proposal](v0.3.0-scope-proposal.md), which audited 26 commits already in the tree, this one is forward-looking: `v0.4.0` has zero issues filed and zero commits against it today. Its job is to propose what to build, grounded in what already exists, not to check a hypothesis against finished work.

It reaches one finding that reframes the release before proposing anything: **most of what the outcome names is already built.** [What that means for scope](#the-finding-that-reframes-this-release). The real new work is narrower than the roadmap line suggests, and naming it precisely is most of this document.

## The finding that reframes this release

The roadmap outcome names three things: compilation, runtime behavior, and program output, graded from prevalidated content with no arbitrary execution. All three are already true of 44 of the 150 published Java SE 21 questions, today, on `main`:

- [ADR 0011](../adr/0011-grade-content-evidence.md) already requires exactly this kind of question to carry mechanical proof, not editorial assertion.
- `src/test/java/dev/certforge/questionbank/internal/ContentPackTest.java` already compiles each question's `Main.java` with `javax.tools.JavaCompiler` pinned to `--release 21`, runs it, and asserts its output matches a committed `expected.txt` — or, for a question about a compile error, asserts the compiler rejects it with the claimed diagnostic. This runs in CI on every change, via `just test-backend`.
- 44 of the 150 Java SE 21 questions' prompts already contain a fenced ` ```java ` block with a real, multi-line program (for example `content/java-se-21/t01-integer-division-assignment/Main.java`, a five-line class whose output the question asks the learner to predict) — a learner practicing "what does this program print" today, not hypothetically.
- [ADR 0006](../adr/0006-isolate-code-execution.md) already defers learner-executed code to `v0.5.0` on purpose: "Operational complexity is intentionally deferred until v0.5.0." `v0.4.0` existing *before* the runner, grading from prevalidated content only, is the plan as already written, not a new decision this release makes.
- The question type is already right: every sampled code-analysis question is `SINGLE_CHOICE`. "Predict the output among four options" and "predict the diagnostic" both fit it with no schema change.

**None of that is new work.** A scope proposal that treated "compilation, runtime behavior, program output, prevalidated" as `v0.4.0`'s job would be proposing to re-announce `v0.3.0`'s content pack under a new name.

**What is not already true: the presentation.** `web/src/ui/Prompt.tsx` renders a fenced code block as plain monospace text — `<pre><code>{text}</code></pre>`, with an explicit comment that the text is "never inserted as HTML" (a stated security property). `web/package.json` has no syntax-highlighting dependency at all. A learner reading `t01-integer-division-assignment`'s five lines today sees them in the same typeface and color as everything else on the page. That is the one part of the roadmap's outcome this project has not built, and it is what "high-quality code presentation" in the roadmap's own wording is naming.

## The constraint that decides how to fix it

Any syntax-highlighting library is a candidate only if it survives this project's existing release gate. `deploy/verify-release.sh` checks the response headers of a real release image for a Content-Security-Policy that includes `style-src 'self'` (`docs/architecture/threat-model.md` records this control, with the end-to-end suite failing on any CSP violation as its proof). The common way syntax highlighters style tokens — `react-syntax-highlighter`'s default mode, among others — writes a `style="color: ..."` attribute onto each token inline. That is exactly what `style-src 'self'` exists to block, and it would fail a gate this project already enforces, not one `v0.4.0` would be inventing.

The fix is a choice of *mode*, not a different library: `react-syntax-highlighter` (built on PrismJS) supports `useInlineStyles={false}`, which emits CSS class names (`token keyword`, `token string`, …) instead of inline styles, from a stylesheet served from the app's own origin. Its tokenizer still produces a tree of React elements, not raw HTML — `Prompt.tsx`'s "never inserted as HTML" property survives either styling mode, only the *mode* has to be pinned correctly. The library accepts `PreTag`/`CodeTag` overrides, so the existing `tabIndex={0}` keyboard-focusability and `aria-label` carry over unchanged.

A theme still needs choosing or writing, and whichever one is chosen needs a contrast check in both color schemes — this project's existing accessibility gate (axe in both color schemes, carried through every readiness review since `v0.1.0`) does not exempt syntax-highlighted tokens from passing it.

## Which content, and which track

**Stays inside Java SE 21. Not a new pack.** The interview track's conceptually adjacent content (`content/java-backend-interview`'s `iv286-*` items — concurrency, the JVM memory model) has zero mechanical proof behind it: `find content/java-backend-interview -name Main.java` finds nothing. Those questions are Asserted-tier, reference-backed, reviewed by citation rather than by a compiler and a captured run. Building `Main.java`/`expected.txt` pairs for them would be real, valuable work — and it is a different piece of work from this release, closer to #80's existing unreviewed-question backlog than to "Code Analysis," and it would compete with Interview Prep's own 18 open issues for the one reviewer this project has rather than with `v0.4.0`'s.

The infrastructure/certification packs (Docker, Kubernetes, Terraform) already have their own evidence mechanism (`content/evidence.mjs`'s `shell-static-check`/`yaml-static-check`), built for a different purpose and not a candidate for this release either.

So the content question is not "which track" — it already has an answer, Java SE 21 — but "how much more." The pack's existing 150 questions already cover the ten published topics at five-per-topic depth (the same count the mock exam blueprint, [ADR 0015](../adr/0015-separate-mock-exam-aggregate.md), depends on). More code-analysis-style questions are optional upside for this release, not required by its outcome: the outcome is met by the 44 that exist, once they are presented well. Proposed: **no new content is required to tag**; more is welcome if review capacity allows once the presentation work is done, in the same small-batch, reviewed-before-published discipline every other pack already follows.

## Review capacity, stated plainly

The roadmap's own rule: a parallel content direction "is worked only when no numbered release is in flight," because review capacity, not engineering capacity, is this project's real constraint (`docs/roadmap/releases.md`, citing [ADR 0005](../adr/0005-ai-not-source-of-truth.md)). Opening `v0.4.0` means Interview Prep's 18 open issues stay exactly where they are — paused, not abandoned — for as long as `v0.4.0` is in flight. That is already the written policy, not a new tradeoff this document is inventing, but it is worth saying once in the open rather than only implied by a table.

## Proposed scope

### In

**Syntax-highlighted code presentation.** `Prompt.tsx`'s fenced-code branch renders through a tokenizer producing React elements (not HTML injection), styled via CSS classes from the app's own stylesheet (`style-src 'self'`-compatible), keyboard-focusable and labeled exactly as today, with a theme checked for contrast in both color schemes.

**Nothing else changes about how a question is authored, reviewed, or graded.** `ContentPackTest`'s compile-run-check mechanism, the `SINGLE_CHOICE` type, and ADR 0006/0011's no-arbitrary-execution policy are already correct and already shipped; this release does not touch them.

**Carried, not claimed.** The 44 existing code-analysis questions ship in the tag because they are already in the tree and already proven; they are not new work this release produces, and the release notes must say so rather than imply they were authored for `v0.4.0`.

### Out

Any new content pack. Backfilling mechanical proof for the interview track's `iv286-*` concurrency items (a real, separate piece of work, not this release's). A new `QuestionType`. Learner-submitted or learner-executed code in any form (`v0.5.0`'s job, by ADR 0006). A code editor, autocomplete, or any interactive code-writing surface. Interview Prep content (paused per the roadmap's own rule while this is in flight).

## Acceptance criteria

- A fenced code block in a question prompt renders with real syntax highlighting (keywords, strings, literals, comments distinguished), via CSS classes from the app's own stylesheet, with no inline `style` attribute on any token.
- The release image's Content-Security-Policy still passes `deploy/verify-release.sh`'s existing check unchanged — this release adds a stylesheet, not a new CSP exception.
- The code block remains keyboard-focusable with its existing `aria-label`, and passes the existing axe check in both color schemes with the new theme in place.
- No question text is ever inserted as raw HTML — the property `Prompt.tsx`'s own comment already states, re-verified after the change, not assumed to survive it.
- The 44 existing code-analysis questions are identifiable as such (a stated list or a tag), so "a learner practices compilation/runtime/output questions" is a claim about named content, not an inference from the pack's total count.

## What this does not amount to

- **This release adds no new reviewed content.** If the owner wants more code-analysis questions, that is additional scope to decide separately, reviewed in the same small batches as every other pack, not a byproduct of shipping syntax highlighting.
- **The interview track's own runtime-behavior questions (`iv286-*`) remain Asserted-tier, unproven by a compiler.** Nothing here changes that; naming it is a limitation this document carries forward, not a gap `v0.4.0` closes.
- **This is not the runner.** `v0.5.0` is a different, larger piece of work (a separately deployed, resource-bounded execution environment) that this release deliberately still does not build, per ADR 0006's own stated sequencing.
- **A learner cannot submit or modify code anywhere in the product after this release**, same as before it.

**Blockers**

- [ ] Pick the syntax-highlighting approach (`react-syntax-highlighter` with `useInlineStyles={false}`, or an equivalent that produces CSS classes rather than inline styles) and confirm `deploy/verify-release.sh`'s CSP check still passes against a real release image.
- [ ] Choose or write a theme and run the existing accessibility suite (axe, both color schemes) against pages containing a code block.
- [ ] Decide whether any new content is in scope for this tag, and if so, how many questions and reviewed by whom, before authoring starts.

**Demonstrability**

- [ ] Walk a code-analysis question (e.g. `t01-integer-division-assignment`) in a browser in both color schemes and confirm the code is legibly highlighted, not just present.
- [ ] Confirm keyboard-only navigation still reaches and scrolls the code block, and a screen reader still announces it via the existing `aria-label`.

**Gates and paperwork**

- [ ] Write `docs/release/v0.4.0-readiness.md` and `docs/release/v0.4.0-release-notes.md`, with pt-BR counterparts, each with a "what this does not amount to" section.

## Explicitly deferred

A code editor or any learner-submitted code. Execution of any kind (`v0.5.0`). A new content pack. Backfilling mechanical proof for interview-track runtime-behavior questions. Interview Prep content generally, while this release is in flight, per the roadmap's own review-capacity rule.
